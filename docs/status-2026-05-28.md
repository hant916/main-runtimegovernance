## 6. 详细的待改进项（深度分析）

### 6.1 [高优先级] `requires_previous_steps` 是死字段

**事实**：
- [Policy.requires_previous_steps](src/ailuros/models/policy.py#L36) 字段已定义
- [PolicyValidator](src/ailuros/policy/validator.py#L23) 在加载时检查它的结构合法性
- **PolicyEngine / PolicyMatcher / DecisionResolver 全部不读这个字段**（grep 结果只有上述两处出现）

**影响**：用户写 `{"requires_previous_steps": {...}}` 不会报错也不会生效——这是 silent failure，比未实现更糟糕。

**应该做的**：
1. 在 `ToolCallContext` 里塞入 `prior_events: list[RuntimeEvent]`（来源于 `storage.list_events(run_id)`）
2. `PolicyMatcher` 增加 `_match_previous_steps()`：用现有的 12 个操作符在历史事件上跑匹配
3. 加 5-8 个测试覆盖：依赖事件存在/不存在、按顺序、最近 N 个

**预估**：~150 行代码 + 测试，半天工作量。

### 6.2 [高优先级] SQLite 序列号有并发竞争

**事实**：[sqlite_storage.py](src/ailuros/storage/sqlite_storage.py) 的 `append_event()` 用：
```python
cursor.execute("SELECT COALESCE(MAX(sequence), 0) + 1 FROM events WHERE run_id = ?", (run_id,))
next_seq = cursor.fetchone()[0]
cursor.execute("INSERT INTO events ... (sequence) VALUES (?)", (next_seq,))
```

两个线程同时 append 同一个 run 的 event 时，两个都拿到相同的 `next_seq`，第二个 INSERT 会撞 `UNIQUE(run_id, sequence)` 约束失败。

**当前掩盖原因**：所有测试都单线程；refund demo 单线程；HTTP server 是只读所以不写。

**应该做的**：
- 方案 A：用 `BEGIN IMMEDIATE` 包住 SELECT+INSERT
- 方案 B：用 `INSERT ... RETURNING sequence` + SQLite trigger 自动算
- 方案 C：去掉 per-run sequence，全局 AUTOINCREMENT + 加 `created_at` 排序

**推荐方案 A**——改动最小，且符合 SQLite 文档对并发写入的建议。

### 6.3 [中优先级] HTTP 服务器无鉴权

**事实**：[server/app.py](src/ailuros/server/app.py) 默认 bind `127.0.0.1`，任何能访问 localhost 的进程都能读所有 timeline——包括其他用户的 run、敏感 payload。

**应该做的**：
- 加 `--token` flag，未匹配返回 401
- 文档中明确"不要直接暴露到公网"
- 评估是否应当默认拒绝非 localhost 请求

### 6.4 [中优先级] 列表端点全部无分页

**事实**：`GET /runs`、`GET /evaluations`、`GET /runs/{id}/replay` 全量返回；`list_events()` 同样无 limit。一次 run 跑出几十万事件后，单个 replay 请求会拖垮进程。

**应该做的**：
- API：加 `?limit=` / `?offset=` 或 `?after=<sequence>`
- 存储层：`list_events(run_id, limit=None, offset=0)`
- CLI 同步加 `--limit` flag

### 6.5 [中优先级] `governance_decisions` / `evaluations` / `audit_reports` 缺 run_id 索引

**事实**：[001_initial.sql](src/ailuros/storage/migrations/001_initial.sql) 只为 `events(run_id, sequence)` 建了索引。其他三张表用 `run_id` 查询时全表扫描。

**应该做的**：建 002_indexes.sql 迁移：
```sql
CREATE INDEX IF NOT EXISTS idx_decisions_run ON governance_decisions(run_id);
CREATE INDEX IF NOT EXISTS idx_evaluations_run ON evaluations(run_id);
CREATE INDEX IF NOT EXISTS idx_audit_run ON audit_reports(run_id);
```

### 6.6 [中优先级] `SANITIZE` / `WARN` 语义不完整

**事实**：
- [DecisionResolver](src/ailuros/policy/decision_resolver.py#L41) 把 `WARN` 当作 `allowed=True`（继续执行 + 留痕），把 `SANITIZE` 当作 `allowed=False`（拦截）
- **没有"sanitize 修改参数"的实现** —— policy 不能描述"把 X 字段脱敏后放行"

**两个选择**：
- 短期：把 `SANITIZE` 在 README 中**明确为"等同 require_review"**，避免误导
- 长期：实现真正的参数转换 —— policy 增加 `sanitize_rules` 字段，runtime 在执行前应用

### 6.7 [中优先级] 无日志输出

**事实**：grep `import logging` 在 src/ 下零结果。运行时完全静默——CLI 输出只在 CLI 命令里手写 `typer.echo`，runtime 内部任何决策都不写日志。

**生产场景影响**：故障排查只能靠 timeline 数据库本身，没有任何 stderr 痕迹。

**应该做的**：加 `ailuros.logging` 模块，runtime 关键节点（before_tool_call decision、policy match、storage corruption）按 INFO/WARN/ERROR 输出。

### 6.8 [中优先级] CLI 无 JSON 输出

**事实**：所有 CLI 命令都是给人看的格式。`audit`、`eval`、`replay`、`run show` 全是 `typer.echo(...)`，无 `--output json`。

**影响**：CI / 监控脚本 / EverRun 集成必须解析人类可读文本，脆弱。

**应该做的**：每个命令加 `--output` 选项（`text` / `json`），默认 text。

### 6.9 [低优先级] `version` 硬编码

**事实**：[cli.py](src/ailuros/cli.py) 中 `@app.command()` `version` 输出固定 `"0.0.0"`，与 [pyproject.toml:7](pyproject.toml#L7) `version = "0.0.0"` 同步——但当 `pyproject.toml` 升到 0.1.0 时 CLI 不会自动跟上。

**应该做的**：`from importlib.metadata import version; version("ailuros")`。

### 6.10 [低优先级] EverRun 三个 checkpoint commit 信息不规范

**事实**：`8cad05d` / `f1e58bb` / `77c48df` 三个 commit 都叫 `everrun: checkpoint state ...`，破坏了 conventional commits 习惯。

**应该做的**：交互式 rebase 重写为 `feat(adapter)` / `feat(server)` / `feat(server/eval)`，附带 EverRun pack 引用。

### 6.11 [低优先级] 缺少框架适配器

**事实**：README 承诺的 LangChain / LlamaIndex / AutoGen / CrewAI 都不存在；现有的 `LocalCallableAdapter` 只是骨架。

**这是 v0.2 的产品边界问题，不是 bug**：
- adapter contract 已经确定且测试过
- 完整框架适配器需要每个框架单独开发 + 测试集成
- 优先级看用户实际使用的是哪个框架

### 6.12 [低优先级] 文档结构

- 没有 `CHANGELOG.md`
- 没有 `CONTRIBUTING.md`
- 没有 API reference（mkdocs / sphinx 都没有起）
- examples 只有一个 refund demo

## 10. 风险清单

| 风险 | 严重度 | 现状 |
|---|---|---|
| `requires_previous_steps` silent failure | **高** | 字段存在 + validator 检查格式 + engine 完全无视 → 用户写了不会报错也不生效 |
| SQLite 并发写竞争 | **中** | 当前单线程未触发，但 server + adapter 并发用会爆 |
| HTTP server 无鉴权 | **中** | 默认 127.0.0.1 减轻，但不应该完全无 token |
| 没有日志 | **中** | 故障排查全靠 storage |
| 没有真实的 framework adapter | **低**（产品定位） | README 承诺了，但 v0.1 范围未交付 |
| `SANITIZE` 语义模糊 | **低** | 现在被当 block 处理，但 enum 名字暗示参数转换 |
| CLI version 硬编码 | **低** | 一行修复 |

**当前无 P0 阻断性风险**——所有问题都是"用户进入特定场景才暴露"，stable baseline 仍然可用。
